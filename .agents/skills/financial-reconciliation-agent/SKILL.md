# Financial Reconciliation 财务业务对账与资金轧差规范

遵循复式记账法（Double-Entry Bookkeeping）与银行级清结算三方对账标准。用于在系统持续运营期（Phase 09 Operations），自动比对内部业务订单、支付网关流水与外部渠道结算单，识别长款、短款、状态不符与金额差异，建立不可篡改的日终平账凭证与资金安全防线。

---

## 1. 何时启用

- **日常日终轧差与对账 (Daily Settlement)**：每日凌晨自动拉取微信支付/支付宝/银联外部对账单并与内部流水对账。
- **租户资金账户平衡性核验**：验证租户钱包、商户待结算余额与变动明细满足“期初 + 收入 - 支出 = 期末”。
- **长款与短款差错处理**：自动归类外部有内部无（长款）、内部有外部无（短款）及金额差异单据，并触发补单或冲正。
- **财务审计与结算准出**：生成月度结算单、向运营人员输出带数字签名的平账报告。

### 1. 差错单处理标准矩阵
| 差错类型 | 典型场景 | 处置策略 | 自动化动作 |
|---|---|---|---|
| **短款 (单边扣款)** | 客户已扣款，但因网络超时内部未收到支付回调通知 | 自动补单并恢复履约 | 从外部对账单获取交易号，调用支付域补发入账事件，更新订单为已支付 |
| **长款 (未扣实履)** | 内部记录成功但外部无此笔流水（罕见，通常为测试数据或伪造请求） | 冻结商户结算资金并告警 | 立即挂起该笔订单，生成高危审计工单，人工介入核验 |
| **金额不符** | 汇率折算误差、手续费扣除口径不一致、黑客篡改实付金额 | 拦截结算并差额挂账 | 将差额部分记入系统暂收暂付挂账账户，通知财务核实 |
| **状态不一致** | 外部渠道已全额退款，内部因重试丢失处于部分退款中 | 状态对齐同步 | 触发向外部渠道主动发起查询并更新本地退款状态 |

## 3. 复式记账平衡性守卫

系统资金变动必须满足复式记账守卫公式：
$$\sum \text{Debit (借方发生额)} \equiv \sum \text{Credit (贷方发生额)}$$
$$\text{期初余额} + \text{借方净变动} - \text{贷方净变动} = \text{期末余额}$$

在对账测试与日常日结中，系统将对所有租户资金账户执行全量对账扫描。一旦发生任何单边账（不平衡），立即阻断结算通道！

## 4. 与 cooliebase-all-base 架构联动

1. **领域边界与契约隔离**：
   - 对账 Agent 属于 `09_operations` 运营域与 `pay` 支付域的协同编排。
   - 必须通过 `payDomainFacade` 或支付插件契约访问交易记录，禁止跨库直查原始数据库表。
2. **多租户数据隔离安全**：
   - 资金账本和对账单必须严格挂载 `tenant_id` 过滤器与 8 大审计底座字段。
   - 运营人员仅可查看其所属租户的对账明细，平台超级管理员在审计视图中必须保留完整不可篡改的操作审计日志。
3. **自动化运营命令联动**：
   - 使用运营体检工具：`npm run agent:ops -- pay.order health`
   - 对账差错扫描与数据样例：`npm run agent:ops -- pay.reconciliation seed-sample`

## 6. 严禁事项

1. **严禁单边账直接修改余额**：严禁财务或管理员手工直接 UPDATE 用户钱包余额表；所有金额变更必须有对应的凭证事件与明细流水！
2. **严禁无审计日志抹账**：严禁对差异单据进行“静默删除”或“直接平账”；必须记录调账人、审批依据与调账说明。
3. **严禁未对账直接放行提现**：在日终对账完成且轧差平衡前，严禁批量触发商户提现或资金划转指令。
