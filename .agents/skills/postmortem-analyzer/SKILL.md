# Postmortem Analyzer 事故免责复盘与根因分析规范

遵循 Google SRE 免责复盘（Blameless Postmortem）文化与 1-5-10 故障应急响应准则。用于在系统发生线上故障、降级或数据不一致事件后，深入剖析系统设计韧性、观测盲区与流程漏洞，通过 5-Whys 根本原因分析与 CAPA（纠正与预防措施）闭环，将每一次故障转化为工程底座的抗脆弱性进化。

---

## 1. 何时启用

- **P1/P2 生产故障恢复后**：全站不可用、核心交易受阻、数据脏写或跨租户隔离穿透。
- **降级演练发现薄弱点**：混沌工程（Chaos Engineering）或断网压测暴露单点故障。
- **发布回滚事件后**：运行手册执行失败触发自动回滚，需查明根本动因。
- **跨域调用雪崩事件**：服务总线重试风暴引发数据库连接池耗尽。

---

## 2. 故障复盘四大黄金铁律

1. **绝对免责原则 (Blameless)**：假定所有人都是在当时掌握的信息下做出的最合理决策；故障的根本原因永远在于**系统设计缺乏防御纵深**与**门禁工具未能拦截**，严禁归咎于“个人粗心”或“操作失误”。
2. **1-5-10 应急时效复盘**：
   - **1 分钟发现**：监控 SLI 燃烧率与 APM 告警是否在 60 秒内触发？
   - **5 分钟响应**：On-Call 人员与应急应急小组是否在 5 分钟内集结？
   - **10 分钟恢复**：是否具备止血手段（Feature Flag、自动回滚、限流熔断），在 10 分钟内完成业务止血？
3. **5-Whys 追根究底**：层层穿透表象，直至找到架构架构缺陷、测试用例遗漏或自动化门禁缺失。
4. **Action Items (CAPA) 必须工程化落地**：每个整改项必须具备明确责任人、GitHub Issue 编号、代码门禁分支，且必须在 14 天内闭环。

## 3. 标准免责复盘报告模版

文件存放位置：`docs/08_sre/06_incidents_postmortem/POSTMORTEM-<YYYYMMDD>-<INCIDENT-NAME>.md`。

```markdown
# 事故复盘报告: [2026-09-20] 营销优惠券并发超发故障

| 事故级别 | 持续时长 | 影响用户/租户数 | 资金损失/业务影响 |
|---|---|---|---|
| P2 (严重) | 28 分钟 | 3 个商户租户，共 142 笔订单 | 超发优惠券 5,000 元（已全部冻结冲正） |

## 1. 事故全景时间线 (Timeline - 1-5-10 评估)
- **14:02** 营销中心上线秒杀活动配置。
- **14:05** 秒杀流量激增，瞬时 QPS 从 500 攀升至 8,000。
- **14:06 (1m 发现 - 达标)** APM 告警触发：库存扣减数据库连接池饱和度达 95%。
- **14:09 (4m 响应 - 达标)** SRE 与业务核心人员进入 War Room。
- **14:20** 发现优惠券库存扣减未加 CAS 乐观锁，出现并发超卖。
- **14:34 (28m 恢复 - 超时 18m)** 紧急下发 Traefik 边缘限流规则，并热部署 CAS 扣减补丁，业务恢复正常。

## 2. 5-Whys 根本原因深入推导 (5-Whys Root Cause Analysis)
1. **为什么优惠券被超发了？**
   因为多个并发请求读取到了相同的剩余库存并重复执行了扣减。
2. **为什么读取到相同库存会重复扣减？**
   因为底层 SQL 使用了无版本控制的 `UPDATE coupon SET stock = stock - 1`，未加 CAS 乐观锁。
3. **为什么没有使用仓库标准的 BaseMapper 原子原子操作？**
   因为新同学误用了自定义 raw SQL 更新，跳过了框架底层内置的条件校验。
4. **为什么在集成测试和代码评审中没有发现？**
   因为针对该接口的单元测试使用了假 Mock（Mock 了数据库返回值），未运行多线程并发测试。
5. **为什么自动化门禁没有拦截假 Mock 和并发缺陷？**
   因为此前变异测试（Mutation Testing）尚未覆盖优惠券领域，导致假测试蒙混过关。

## 3. 经验总结与防御纵深反思 (Lessons Learned)
### 做得好的地方 (What went well)
- APM 告警及时，在 1 分钟内准确捕捉到连接池饱和度异动。
- 业务设计支持资金事后冻结与对账冲正，未造成实际坏账。

### 做得不足的地方 (Where we got lucky / What went wrong)
- 恢复时长耗时 28 分钟，未能达成 10 分钟快速止血目标（缺乏一键降级开关）。
- 测试套件存在假 Mock 毒瘤。

## 4. 纠正与预防措施清单 (CAPA - Action Items)
| 措施类型 | 具体行动事项 | 对应责任人 | 关联 Issue / PR | 交付时限 | 验收标准 |
|---|---|---|---|---|---|
| **防重复发生** | 将优惠券扣减重构为真实嵌入式 SQLite CAS 乐观锁 | @dev-lead | #342 | 2026-09-22 | 通过并发 100 线程竞争单测 |
| **测试防御** | 引入 `mutation-tester` 变异测试，将变异得分提升至 $\ge 85\%$ | @qa-lead | #345 | 2026-09-25 | 注入无版本锁变异体时测试必须红牌 |
| **观测与止血** | 在 Traefik 网关层配置基于租户的动态降级熔断规则 | @sre-lead | #348 | 2026-09-26 | 演练达成 3 分钟内一键熔断止血 |
```

## 4. 与 cooliebase-all 架构联动

1. **CAPA 闭环机制**：
   - 所有的代码修复动作必须伴随针对性的真实数据库集成测试（`test/integration/`）。
   - 验证命令：`npm run test:matrix` 与 `npm run check`。
2. **知识资产沉淀**：
   - 复盘产物归档于 `docs/08_sre/06_incidents_postmortem/`，并同步更新 OpenWiki 故障案例库。

---

## 5. 检查清单与门禁

- [ ] 复盘报告是否严格秉持免责态度，杜绝任何指责个人的措辞？
- [ ] 5-Whys 是否追溯到了系统架构、自动化门禁或防御机制层面的根因？
- [ ] 时间线还原是否对标了 1-5-10 指标并说明耗时超时原因？
- [ ] 每条 CAPA 措施是否均包含责任人、落地 Issue、明确验收标准与时限？
- [ ] 对应修复 PR 是否补充了真实数据库并发反假 Mock 测试？

---

## 6. 严禁事项

1. **严禁指责与惩罚个人**：严禁在复盘报告中写“某员工粗心大意导致问题”等非工程性归因。
2. **严禁无工程动作的口头保证**：严禁将“加强人员培训”、“下次注意”作为 CAPA 预防措施。
3. **严禁故障复盘烂尾**：制定的 Action Items 必须追踪至 PR 合并，严禁只写文档不实施代码变更。
