# 给 coolie 工坊的迁移提案：多 CLI Hook 接入 + 门禁方法论

> **性质**：提案。**本文件不修改 coolie 仓库的任何内容**，由 coolie 的开发者自行决定取舍。
> **来源**：`cooliebase-all` 在 2026-10 的多轮实测。凡标「**实测**」的，都是在本仓**真跑过并踩到过**的，
> 不是设计推演。凡标「**别照抄**」的，是本仓特有条件，硬搬会变成负担。
>
> 引用本仓文件时给的是**相对路径**，方便对照——不是说必须按同样目录组织。

---

## 0. 三句话摘要

1. **想让 hook 被多家 AI CLI 识别**：只需一个**守卫脚本** + 每家一份**薄适配**；
   协议取**最小公约数**（stdin JSON + `exit 2` + stderr），**载荷解析要兼容多种字段名**。
2. **想让它真的拦得住**：靠四层里**唯一跨 CLI 的那一层**（git 钩子）兜底，再加 CI 兜 git 钩子。
3. **想让它长期不腐烂**：每条门禁都必须**证明自己能失败**（反向对照），
   并且用**注册表 + 覆盖检查**防「新加的东西没接线」。

---

## 1. 多 CLI Hook：能直接搬的部分

### 1.1 结构（三个文件足矣）

```
<repo>/.agents/hooks/spec-gate.sh        ← 唯一守卫脚本（所有家都指向它）
<repo>/.agents/hooks/parse-payload.js    ← 载荷解析（兼容各家字段名）
<repo>/.agents/hooks/adapters.json       ← 适配器注册表（见 §1.5）
```

各家配置里**只写一行命令**指向 `spec-gate.sh`，**不要**把判定逻辑复制到各家配置里。

### 1.2 协议：取最小公约数（实测有效）

```
stdin  : 一段 JSON（各家字段名不同，见 §1.3）
stdout : 允许时保持安静（多余输出会被某些家当噪音回灌给模型）
stderr : 拦截原因（要**可操作**：写清"违反了哪条 + 确切修法"）
exit 2 : 拦截（cmd 与 Hermes 共同承认的协议；exit 0 = 放行）
```

**实测教训**：只认一种载荷字段，会在某一家上**静默失效**——hook 不报错、也不拦，
看起来一切正常。所以解析层要**列出多候选字段**并逐个尝试：

```js
// .agents/hooks/parse-payload.js 的候选顺序（本仓实测集合）
const CANDIDATES = [
  "tool_input.file_path",   // cmd / Claude
  "tool_input.path",
  "tool_input.absolute_path",
  "args.file_path",         // Hermes
  "args.path",
]
```

### 1.3 各家的差异（本仓已取证的 4 家）

| CLI | 读哪个指令文件 | 配置位置 | 事件名 |
|---|---|---|---|
| Command Code (`cmd`) | `AGENTS.md` | `.commandcode/settings.json` | `PreToolUse` / `SessionStart` |
| Claude Code | `CLAUDE.md` | `.claude/settings.json` | `PreToolUse`（带 `matcher`） |
| Antigravity (`agy`) | `AGENTS.md` + `GEMINI.md` + **`.agents/rules/*.md`** | `.agents/hooks.json` | `PreToolUse` |
| Hermes | 自动注入 `AGENTS.md` | `~/.hermes/config.yaml`（**用户级，仓内不可提交**） | `pre_tool_call` |

**差异点**（都是实测踩出来的）：
- 变量展开：Claude 用 `$CLAUDE_PROJECT_DIR`，cmd 用 `$COMMANDCODE_PROJECT_DIR`；
  命令里**别用裸相对路径**——工作目录各家不同（agy 的 cwd 曾经是 `.agents/`）。
- Hermes 是**用户级**配置，仓里提交不了 → 给一个**幂等安装脚本**，别让用户手改 YAML。
- 只读 rules 的 CLI（如 Cursor 的 `.cursor/rules`）**拦不住写操作** → 只能靠 git 钩子兜。

### 1.4 四层防线（哪层能挡什么）

| 层 | 执行者 | 能否被模型绕过 | 覆盖范围 | 拦截时机 |
|---|---|---|---|---|
| L0 仓内脚本（如 `agent:route` 之类判定命令） | 仓库脚本 | **能**（模型可以选择不跑） | 全部 | 手动 |
| L1 各 CLI hooks | CLI 引擎 | 不能 | **单家** | 写文件**之前**（体验最好） |
| **L2 git 钩子** | **git** | **不能** | **所有 CLI + 人** | 提交时 |
| L3 CI | CI | 不能 | 全部（合并前） | 合并前 |

**要点**：L1 体验最好但**覆盖面随 CLI 变化**；**L2 是唯一与"你用什么工具"无关的一层**。
所以 L2 不是可选项。

### 1.5 L2 的三个坑（本仓全部踩过）

**坑 1：`core.hooksPath` 在 `.git/config` 里 —— 本机配置，提交不了。**
→ 新克隆**默认没有钩子**。

**坑 2：靠 `postinstall` 装它，隐含要求「`git init` 早于 `npm install`」。**
本仓**孵化产物**上这个时序不成立：`.git` 有、`core.hooksPath` **没有**（实测）。
→ 修法：**每处 `git init` 之后立刻调用同一个启用脚本**（幂等，不依赖安装时序）：

```bash
# 孵化/克隆脚本里，git init 之后
node scripts/setup-git-hooks.cjs || true
```

**坑 3：`git commit --no-verify` 能绕过。**
→ 这是 git 自身机制，**堵不住** → 必须**在 CI 补跑同样的检查**。
本仓实测：有一条检查只挂在 git 钩子上，CI 没补 —— 等于**只防君子**。

### 1.6 用一个"启用脚本"收口（幂等）

```js
// scripts/setup-git-hooks.cjs 的关键行为（本仓实测过的分支）
if (!fs.existsSync(".git")) return            // degit / 复制出来的目录 → 优雅跳过，exit 0
if (!fs.existsSync(".githooks/pre-commit")) return
// 已设且相同 → 打印"已启用"并退出（幂等）
// 设置失败 → **不阻断安装**（钩子是增强，不是安装前置），打印警告
git(["config", "--local", "core.hooksPath", ".githooks"])
```

**为什么失败不阻断**：钩子是**增强**。为它让 `npm install` 失败，会让"想去掉它的人"直接删脚本。

### 1.7 加一个新 CLI 的正确流程（建议做成机检）

1. 支持 hook → 建配置，命令指向**同一个**守卫脚本，并在**注册表**登记 `config`；
2. 只读 rules → 在注册表登记 `mechanism: "rules-only"` + **`reason`（写清依据）**；
3. **注册表要有"覆盖检查"**：仓库里出现的每个 CLI 配置目录都必须登记，否则**门禁失败**。

> **实测动机**：本仓原本把适配器清单**硬编码在测试里** → 新增一个 CLI 目录不会被要求登记、
> 少配一家也全绿。改成"读注册表 + 覆盖检查"后，放一个未登记目录进去 → 测试 **exit 1** 并点名修法。

## 2. 门禁方法论（比 hook 更值钱的部分）

以下 8 条是本仓用**反复踩坑**换来的。建议 coolie 逐条对照，不一定要全做，但**做了的宁可少而真**。

### 2.1 每条门禁都必须**证明自己能失败**

新加一条门禁，必须同时给一条**反向对照**：故意制造一次违规 → 必须**非零退出**。

> **实测**：本仓多次出现「门禁看着有、实际是空的」——
> 例如一条"禁止空转断言"的规则**只扫 3 个目录**，而违规恰好落在没扫到的第 4 个目录上，
> 规则一直是绿的。

### 2.2 反向对照不红时，**先怀疑门禁本身**

> **实测（本轮发生 3 次）**：
> ① 基线键只用文件路径 → 改掉同一文件里的违规值**不产生新键**，拦不住；
> ② `--range` 模式里 before 取 HEAD、after 取 index，提交后**恒等** → **永远不可能失败**；
> ③ 验"钩子能不能拦"时写成 `git commit … | grep …; echo $?` → 取到的是 **grep** 的退出码。
>
> 三次的结论都是：**测量方法坏了，不是被测对象没问题。**

### 2.3 退出码 0 只说明"没崩"，不说明"做了事"

新增门禁后要**核对产物**（数量、内容），不能只看退出码。

> **实测**：一次元数据插入把键名写成了带缩进的 `"          enumValues"`，
> 生成器的退出码是 0，但**写入 0 份**——是核对"到底有没有生成"才发现的。

### 2.4 只做"能对标真源"的检查；**范围窄是零误报的前提**

- 只扫**确定能对标**的地方（如只扫 2 个目录），命中但**对标不到真源的一律不检查**（宁可漏，不可误报）。
- **真源缺失要报错，不能静默通过**。

> **实测**：全仓扫描"路径引用是否真实存在"→ 62 处不存在里约 26 处是**合法**的
> （反例语境 / 外部项目 / 示例），全是误报。收窄到"只扫生成物"后 → 零误报。

### 2.5 存量欠债用**棘轮**，不要一次全红

- **新增违规必须挡**；**存量欠债冻结在基线文件**里，等有空再还。
- 一次全红会逼出"无意义豁免"——**豁免比违规更难发现**。

```
tier: ratchet  →  基线 JSON（含 note：说明为什么不完全清零）
本轮新增 > 0   →  失败，并打印"怎么修"与"--write-baseline（确认后收紧）"
```

### 2.6 **注册表 + 覆盖检查**（本仓反复出现的同一个模式）

凡是"有一组同类东西必须保持一致"的地方，都用这个模式：

| 本仓用法 | 覆盖什么 |
|---|---|
| 域目录注册表 | 新增域必须登记 |
| 技能注册表 | 技能单一真源（禁止副本目录） |
| **规则 ↔ 提示装配表** | 新增规则必须被 AI 入口加载（见 §3.1） |
| **CLI 适配器注册表** | 新增 CLI 目录必须接线（见 §1.7） |
| **文档声明机检** | 文档里写死的数字必须与真源一致 |

**关键在"覆盖"二字**：不是抽查一个，而是**枚举全量 + 断言差集为空**。

### 2.7 门禁要**接进唯一的入口链**，且**每个人都会跑到**

- 一条命令跑完全部静态门禁（本仓是 `pnpm run check`），**新门禁必须登记进去**。
- 否则"门禁存在"与"门禁被执行"是两回事。

### 2.8 每轮记录**真实退出码**，不写"应该没问题"

```
本轮:  check EXIT=0 / 反向对照 EXIT=1 / 契约测试 3 files 5 tests
```

## 3. AI 协作过程：两条容易忽略的

### 3.1 规则**写了不等于 AI 看得到**（本仓实测）

本仓把规则拆成多个文件，另有一份"提示装配表"声明**按什么顺序加载哪些片段**。
实测：**9 个规则文件里只有 5 个注册进了装配表** —— 剩下 4 个（含刚写的两个）**AI 入口根本看不到**。

> **建议 coolie**：如果 coolie 也有类似的分段装配 / rules 目录，
> 加一条机检：**磁盘上的每个规则文件都必须出现在装配表里**（反向也要查：装配表不得引用不存在的文件）。

### 3.2 文档里写死的数字**一定会漂**

> **实测**：本仓连续多轮栽在同一件事上——
> 「活跃规格 8 份」实际 12、「门禁 13」实际 20、「规范规则 11」实际 17……
> 更糟的一次：文档写着「这些数字由某个门禁守着」，**同一文件下一行**又自认「本文件不在被检列表内」。

**两条建议**：
1. **能引用的不写死**：写「见 `xx:check` 的输出」而不是具体数字。
2. 真要写死，就**建机检**：把"可核验的声明"列成表，逐条与真源对照（只扫**确定能对标**的目录）。

## 4. 建议的落地顺序（从便宜到贵）

| 步 | 做什么 | 验收（可执行） |
|---|---|---|
| 1 | 写**一个**守卫脚本（先只做一条最容易判定的规则） | 手动喂一份违规 payload → 脚本 `exit 2` 且 stderr 写清修法 |
| 2 | 接 **1 家** CLI，跑通"写文件被拦" | 在该 CLI 里真实触发一次，看到拦截 |
| 3 | 写**启用脚本** + 接进 `postinstall` | 新克隆 `npm install` 后 `git config --get core.hooksPath` 非空 |
| 4 | **每处 `git init` 之后立刻调用启用脚本** | 孵化/新建的产物里 `core.hooksPath` 非空（**实测过这个坑**） |
| 5 | 接第 2、3 家 CLI，加**注册表 + 覆盖检查** | 放一个未登记的 CLI 目录 → 机检 `exit 1` |
| 6 | **在 CI 补跑 git 钩子里的每条检查** | 故意用一个"只在钩子里"的检查 → `--no-verify` 提交 → CI 必须红 |
| 7 | 把上面的"门禁方法论"逐条对照（§2） | 每条新门禁都有反向对照；存量用棘轮 |

## 5. 明确**别照抄**的部分（本仓特有条件）

1. **本仓的目录组织与命名**（`packages/domains` / `packages/plugins` / `docs/0X_*`）——
   按 coolie 自己的约定来，**不要为了对齐而搬家**。
2. **本仓的具体规则内容**（跨域必须走 Facade、多租户隔离、17 个原生域…）——
   那些是**本仓的业务约束**，与 hook 机制无关。
3. **本仓的工具链命令**（`pnpm run <具体脚本名>`）—— 换成 coolie 自己的脚本名即可。
4. **本仓的棘轮基线数值** —— 基线是"本仓当前的欠债"，**没有任何参考价值**。
5. **把 AGENTS.md 整篇当系统提示** —— 本仓明确禁止（分段装配的初衷就是这个）；
   如果 coolie 的规则文件已经很长，**先分段，再谈加载**。

## 6. 最小可复制清单（照抄这 6 个文件就够起步）

```
.agents/hooks/spec-gate.sh          ← 守卫（唯一判定逻辑）
.agents/hooks/parse-payload.js      ← 载荷解析（多字段候选）
.agents/hooks/adapters.json         ← 注册表（新增 CLI 的落点）
scripts/setup-git-hooks.cjs         ← 幂等启用（postinstall + git init 后调用）
.githooks/pre-commit                ← L2 兜底（与 L1 同源判定，避免两处漂移）
<CI 配置>                            ← L3：补跑 git 钩子里的每条检查
```

**其中「与 L1 同源判定」很关键**：本仓的 `pre-commit` 头部注释明确写着
「判定与 CLI hook 同源，避免两处规则漂移」——**两条路径共用一份判定**，才不会"改了 A 忘了 B"。

---

## 7. 最后一条（也是本仓花代价最大的一条）

**"我说做过了"要换成"可核验的记录"。**

- 产物看**文件**
- 门禁看**退出码**
- 拦截看**真触发一次**
- 未验证的，就说**未验证**（本仓文档里大量保留了「本次未验」的标注，那是特性，不是缺点）

> 本仓在这条上栽过：曾有一个阶段 `check` / `build` / 指纹 / 任务追溯**全绿**，
> 而**登录链是断的** —— 因为门禁测的是**机制**，不是**产品能不能用**。
> 加一条"起服务 + 真登录"的冒烟后，这类问题才被挡住。
> **coolie 如果有类似的"全绿但坏掉"的经历，值得单独加一层。**
