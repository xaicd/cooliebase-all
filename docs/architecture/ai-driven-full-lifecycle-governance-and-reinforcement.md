## 二、 六大阶段具体强化规范与实战落地

---

### 1. 需求阶段强化：【EARS 结构化语法与双向跟踪矩阵 (RTM)】
> **强化依据**: CMMI 3 RD/REQM + OpenAI FDE 结构化澄清协议。

#### 1.1 EARS 统一需求工程语法
大模型在接收人类模糊指令时，严禁直接开工，必须先将需求翻译为 **EARS 五种标准语法**：
1. **泛在需求 (Ubiquitous)**: `系统应当 (The system shall) <系统响应>`。
2. **事件驱动 (Event-driven)**: `当 <触发事件> 发生时，系统应当 <系统响应>`。
3. **状态驱动 (State-driven)**: `当系统处于 <特定状态> 时，系统应当 <系统响应>`。
4. **可选特性 (Optional features)**: `在具备 <特定特性/权限> 的情况下，系统应当 <系统响应>`。
5. **异常行为 (Unwanted behavior)**: `如果 <异常/违规/越权> 发生，那么系统应当 <拦截并告警>`。

#### 1.2 双向需求跟踪矩阵 (RTM) 契约
每一个业务需求必须分配唯一追踪代号（如 `REQ-MALL-ORDER-001`），并建立如下全生命周期穿透卡：
```markdown
[RTM 追踪卡] REQ-MALL-ORDER-001
- 业务目标: 大促秒杀防超卖
- 关联实体: Order, SkuInventory
- 设计 Schema: packages/domains/mall/backend/models/order.prisma
- 接口契约: POST /api/v1/app/mall/orders
- 实现提交: git commit 7a8b9c1d
- 验收用例: packages/domains/mall/backend/services/__tests__/order-seckill.test.ts
- 线上拨测: probe/mall-order-health.sh
```

### 2. 设计阶段强化：【动态业务本体双核与行级多租户物理防线】
> **强化依据**: Palantir Foundry 动态本体架构 + 零信任多租户安全规范。

#### 2.1 业务本体双核驱动 (Object + Action)
严禁将重型业务设计为扁平的“死表 + 离散 CRUD”！必须在架构设计说明书中落实业务双核：
- **Object Types (业务实体孪生)**：
  - 拥有唯一实体主键、强业务状态机（DRAFT -> PENDING -> ACTIVE -> ARCHIVED）；
  - 标明不可篡改的核心守恒量（如账户余额、库存实物数、配额上限）。
- **Action Types (合法业务动词与闭环灵魂)**：
  - 业务状态的一切迁移必须通过合法的 Action 驱动（如 `Order.Approve`、`Order.Refund`、`Stock.Deduct`）；
  - Action 必须具备**前置校验断言 (Pre-conditions)**、**原子事务执行**、**不可变审计流水**与**领域事件广播**。

#### 2.2 行级多租户物理拦截 (Row-Level Tenant Isolation)
- **服务端绝对信任隔离**：严禁相信前端传入的 `tenantId`！
- **中间件层级注入**：在 Next.js Middleware 与 Prisma Client 扩展层自动挂载上下文拦截器：
  ```typescript
  // Prisma 客户端强制多租户切面
  prisma.$extends({
    query: {
      $allModels: {
        async $allOperations({ model, operation, args, query }) {
          const tenantId = TenantContext.getTenantId();
          if (tenantId && isTenantModel(model)) {
            // 物理追加 where 条件，杜绝越权漏洞
            args.where = { ...args.where, tenantId };
          }
          return query(args);
        },
      },
    },
  });
  ```

### 3. 开发阶段强化：【极简两字 UI 契约与移动端 6 寸屏人机工效】
> **强化依据**: 顶级产品总监极简主义 + 现场人机工程学。

#### 3.1 极简两字按钮契约 (Two-Character Action Rule)
在管理端（本仓 `src/app/(admin-pages)/`）与移动端（`clients/expo`）中，所有核心交互动作按钮**100% 收敛为纯 2 汉字**：
- 正向主操作：【创建】、【新建】、【查看】、【发布】、【审批】、【提交】
- 辅助与防护：【驳回】、【放弃】、【重置】、【冻结】、【导出】、【沙箱】
- 严禁任何长文案（如“点击提交审批申请”）与技术代号（如 `PR-xx` / `TypeError`）暴露在 UI 表面。

#### 3.2 移动端 6 寸屏防遮挡与局部 1-Hop 卡片流
- **防键盘顶起遮挡**：移动端所有输入界面强制使用 `<KeyboardAvoidingView behavior={Platform.OS === "ios" ? "padding" : "height"}>` 并包裹可滚动容器；
- **独占模态安全**：弹窗与底部抽屉必须配置 `accessibilityViewIsModal={true}` 与 `backdrop` 防穿透，触控热区保持 `>= 44×44px`；
- **页面四态容器化**：每一个业务界面必须由统一的 `<StateContainer state={status}>` 包裹，严格穷举：
  1. `loading`：骨架屏预占位；
  2. `data`：清晰层次的业务卡片；
  3. `empty`：温和空态插画 + 极简两字操作直达；
  4. `error`：清晰错误说明 + 一键【重试】按钮。

### 4. 测试阶段强化：【拟真人全业务走查与死交互自动嗅探】
> **强化依据**: SpaceX 级反空壳单测 + Palantir DS 业务探路者哲学。

#### 4.1 Playwright / Agent-Browser 拟真人全业务旅程走查
- 单测只证明逻辑没抛错，**不证明业务走得通**；
- 必须基于 Playwright 编写完整的端到端用例，模拟用户真实点击：
  `登录 -> 租户切换 -> 创建单据 -> 审批流转 -> 报表数据一致性核验`；
- 执行过程自动截取带时间戳的真机屏幕快照，归档至 `test-results/evidence/`。

#### 4.2 死交互与假按钮自动嗅探
- **嗅探规则**：遍历 DOM 中所有具备 Button / Pressable 特征的交互点；
- **断言标准**：点击该元素后，必须在 500ms 内检测到以下三者之一发生变化：
  1. URL / 路由状态改变；
  2. 网络发出合法 API 请求；
  3. DOM 触发弹窗/模态/状态更新；
  - 若点击后系统毫无物理变化，直接判定为**“假按钮/死交互缺陷”**，自动化测试硬阻断！

### 5. 运营阶段强化：【AI 数字员工 (NPC / Agent) 治理与预算硬停】
> **强化依据**: Coolie 工坊 Agent 治理控制面核心机制。

重型业务模板必须内置**企业级数字员工运营中枢**，杜绝失控：
1. **复合逻辑实体模型**：业务 Agent 在系统中具备独立的实体记录（包含专属工具池、2字技能列表、汇报关系与调用权限）；
2. **月度预算硬停熔断 (Budget Hard-Stop)**：
   - 为每个 Agent 配置月度配额 `budget_monthly_cents`；
   - 每次调用实时累计花销 `spent_monthly_cents`；
   - 超支自动触发熔断，状态置为 `paused`，挂载原因 `budget_exceeded`，必须经老板审批提额后方可恢复；
3. **高管审批三大直达快道**：
   - 顶栏 🔔 铃铛直通全功能收件箱；
   - 业务工坊会话常驻审批待办横幅；
   - 运营态势大盘提供红灯指标一键穿透。

### 6. 运维阶段强化：【不可变制品指纹、7 处版本一致性与秒级回滚】
> **强化依据**: Palantir Apollo 持续交付架构 + CMMI 3 配置管理 (CM)。

#### 6.1 环境版本指纹握手 (Environment Provenance Handshake)
- 发布前必须通过构建管道生成不可变的制品签名哈希（Commit SHA + 依赖锁摘要 + Docker 镜像 Digest）；
- 部署宿主机启动时，必须打印自身运行态指纹，与部署会签单比对。指纹不一致时立即阻断流量接入，彻底杜绝“本地改完但线上跑旧代码”的灾难。

#### 6.2 全局 7 处版本号一致性守卫
在触发生产发版或打 Tag 时，必须通过自动化脚本校验以下 7 处版本号源 100% 绝对一致：
1. `package.json`
2. `packages/shared/package.json`
3. `clients/expo/app.json`
4. `clients/expo/package.json`
5. `CHANGELOG.md`
6. `version.json`
7. Git Release Tag

#### 6.3 主动健康拨测与秒级回滚 SOP
- 发布后 60 秒内，自动触发关键业务探针（健康探测、登录端点、核心查询接口）；
- 若拨测探针连续 3 次超时或返回 5xx，自动触发容器秒级回滚指令（切换回上一版本 Docker Standalone 镜像），并向飞书/微信运维大盘发出 P0 级报警。
