# 反哺清单（本仓强项 → 通用版）

> **目标**：把本项目**独有且已被真实故障验证**的做法，提炼成可移植的"原则 + 判据"。
> **判据**：每条都必须能回答三问 —— ①它是**什么规则** ②它**拦住了什么真实故障** ③**怎么机检**。
> **DoD**：≥3 条有论证（本文件给了 **8 条**，全部来自本仓近两日的真实提交）。

---

## 1. 「反向对照不红时，先怀疑门禁本身」

**规则**：新增/审查任何门禁，必须构造一次**违规注入**并观察它**非零退出**。
**若它没红，第一嫌疑是门禁坏了，不是被测对象没问题。**

**论证（本仓两日内命中 3 次）**：

| 门禁 | 注入 | 结果 | 真实原因 |
|---|---|---|---|
| `contracts:governance:check` 的棘轮 | 把一个已冻结的契约改成新的未登记前缀 | **exit 0**（假绿） | 基线键只用**文件路径**，改同文件内的值**不产生新键** |
| `plan:freshness --range` | 造"新增 script 不改计划"的提交 | **exit 0** | `before` 取 HEAD、`after` 取 index → **提交后恒等** |
| `hatch:e2e` 的钩子验证 | `git commit … \| grep …; echo $?` | **0** | `$?` 取到的是 **grep** 的退出码 |

**怎么机检**：这不是一条自动规则，而是**流程要求** —— 每道门禁的 PR/提交里必须附一条反向对照记录
（本仓的做法：把反向对照写成**单元测试**，如 `test/unit/doc-claims-gate.test.ts` 里"改错一个数字 → 期望 exit 1"）。

**为什么值得反哺**：绝大多数"门禁"的死法不是没写，而是**写了但永远不会红**，而没人试过让它红。

---

## 2. 「退出码 0 只说明没崩，不说明做了事」

**规则**：**生成/改写类**脚本，成功判据必须是**核对产物**（数量、内容），不能只看 exit code。

**论证（实测）**：一次往表元数据里插 `enumValues`，缩进被错误地包进了引号 ——
写成 `"          enumValues"`（键名带空格 ✓ 语法合法 ✓ 文件能 parse ✓）。
生成器 **exit=0**，但 **写入 0 份**。是"核对到底有没有生成"才发现的。

**怎么机检**：`脚本必须打印计数`（本仓多数脚本都打 `已写入 N 份 / 未变化 M 份`），
并在测试里断言 `N > 0` 或断言产物的**关键字段存在**。

---

## 3. 「注册表 + 覆盖检查」（本仓复用 5 次的同一模式）

**规则**：凡"一组同类东西必须保持一致"的地方，都用：
**一个注册表文件 + 一条"枚举全量、断言差集为空"的门禁**。
**不是抽查一个，而是枚举所有。**

**论证（5 处复用，其中 3 处已抓到真问题）**：

| 注册表 | 覆盖什么 | 抓到过什么 |
|---|---|---|
| `domain-catalog.json` | 17 个域 | — |
| `.agents/skills/*/SKILL.md` | 技能单一真源（禁副本目录） | — |
| **`.agents/context/ASSEMBLY.md`** | 规则是否被 AI 入口加载 | **9 个规则里 4 个没注册** ✗ |
| **`.agents/hooks/adapters.json`** | 新 CLI 目录是否接线 | 放一个未登记目录 → 红 ✓ |
| **`docs/claims` 的真源表** | 文档里写死的数字 | **「活跃规格 8 份」实际 12** ✗ |

**反模式对照**：本仓有一处曾是"**点检冒充满覆盖**" ——
规则挂载只断言 `high-order-inverse-thinking` 一个挂了没挂，其余 8 个漏了也全绿。
**"抽查一个"比"不查"更危险**，因为它给人"已经查过了"的错觉。

---

## 4. 「棘轮：只拦新增，存量冻结在基线里」

**规则**：新门禁上线时，**存量欠债冻结进基线 JSON**（含 `note` 说明为什么不一次清零），
**只拦新增**；修完用 `--write-baseline` 收紧。

**论证**：本仓 `no-new-npm-run` / `no-new-npx` / `agent:routes` 欠债 等都用这个模式。
一次性全红会**逼出"无意义豁免"** —— 而**豁免比违规更难发现**（它看起来是"已处理"）。

**两个必须配套的细节**（本仓都踩过）：
1. **基线键要含"取值"**，不能只用文件路径（否则改文件内的违规值不产生新键 → 拦不住）；
2. **派生工程的基线必须重算** —— 否则"found − baseline"必然非空，
   产生**假阳性**（本仓实测 `no-new-npm-run` 在裁剪后的产物里报 `new debt: 9`）。

---

## 5. 「门禁的每条代码路径都要能被证伪」

**规则**：门禁有多个模式/分支（如"暂存区模式"与"`--range` 模式"）时，
**每个分支都要有独立的反向对照**；只证明"主路径会红"是不够的。

**论证**：`plan:freshness` 的**钩子路径**（读暂存区）是对的 ✓，
但它的 `--range` 路径（给 CI 用）**恒不失败** ✗ —— 而那条路径**从未被任何人跑过**。
如果只满足于"钩子能拦住"，**CI 那道兜底就是装饰**。

---

## 6. 「判断存在性要看取值，不要看键是否存在」

**规则**：配置/环境里判断"是否已配置"时，**读值判断语义**，不要用正则匹配"有没有这个键"。

**论证（本仓同一天踩两次）**：

```js
// ✗ 只看键
const hasDatabaseUrl = /^DATABASE_URL=/m.test(env)        // 已有（哪怕指向旧库）→ 不更新
// 结果：SQLITE_DB_PATH=data/e2e-probe.db
//       DATABASE_URL=file:./data/demo-mall.db   ← 两个变量指向不同的库
//       → 应用连到没种子的库 → 登录 500/401

// ✓ 看取值
const url = (/^DATABASE_URL=(.*)$/m.exec(env)?.[1] ?? "").trim()
const pointsAtNonSqlite = url !== "" && !/^(file:|sqlite:)/i.test(url)
```

第二处：E2E 的"跳过判据"写成 `if (!sqlitePath)`，而该变量**总是被写入** → **永远不跳过**
→ 把 PostgreSQL 产物当 SQLite 验 → 必然 401。

---

## 7. 「跳过要打印理由；跳过 ≠ 放过」

**规则**：任何"因条件不满足而跳过"的检查，必须**显式打印理由**（且理由要指向事实，不是"暂不支持"）。

**论证**：本仓 `hatch:e2e` 对 PostgreSQL 产物**跳过**开箱验活，打印：

```
SKIP create 开箱验活：产物连接的是 PostgreSQL（e2e 内为临时嵌入式实例，进程结束即消失），
无法作为持久库验证登录。
```

这条理由让"跳过"**可审计**：读者能判断"这个跳过是否合理"。
**反例**：静默 `return` 会让"跳过"与"通过"在日志里长得一模一样。

---

## 8. 「报告式 vs 门禁式」的取舍要写明，并附误报统计

**规则**：不是所有检查都该做成失败门禁。**做成 report-only 时必须记录"为什么"以及"误报率"。**

**论证**：本仓 `vacuity:audit`（测试空转度）刻意**不接 `check` 链**，理由是文档里写明的：
三个启发式在本仓 **100% 误报**（弱断言单独出现通常是**正确**的）。
另外 `evolution:backlog` **永不失败** —— 它的职责是暴露欠债，不是阻断。

**为什么值得反哺**：把"为什么不做成门禁"写清楚，比多一道门禁更有价值 ——
否则下一个人会"顺手把它接进 CI"，然后被迫加一堆豁免。

---

## 9. （附）「不假装跑过」

**规则**：未验证的，就写"未验证"，并写清**为什么**（环境限制 / 成本 / 待 CI）。

**论证（本仓做法）**：
- 容器构建：本机 Docker 是 colima-on-Linux-VM，端口未转发 → 明确写"**未验证**"，不写"应该没问题"；
- `smoke:login` 在本机因 **macOS FSEvent 额度耗尽**失败 → 先跑**基座自己**做对照
  （同样失败 → 证明是机器级），再写"**与产物无关**"；
- 审计报告里所有"强项"都附**可交叉验证的提交号**。

**为什么最值得反哺**：**审计的可信度 = 它承认了多少没做到的事。**

## 汇总：本仓可反哺的 9 条

| # | 原则 | 一句话判据 | 本仓证据 |
|---|---|---|---|
| 1 | 反向对照失效先怀疑门禁 | 门禁 PR 必须附"注入即红"的记录 | 3 次假绿（基线键 / `--range` / `$?`） |
| 2 | exit 0 ≠ 做了事 | 生成类脚本必须打印并断言计数 | 写入 0 份而 exit 0 |
| 3 | 注册表 + 覆盖检查 | 枚举全量 + 差集为空（不是抽查一个） | 5 处复用，3 处抓到真问题 |
| 4 | 棘轮只拦新增 | 存量冻结 + 键含取值 + 派生工程重算 | `no-new-npm-run` 假阳性 |
| 5 | 每条代码路径都要能证伪 | 多分支门禁各有反向对照 | `--range` 恒不失败 |
| 6 | 看取值不看键 | 判断已配置时读值判语义 | 同一天踩两次 → 登录 500/401 |
| 7 | 跳过必须打印理由 | 跳过与通过要在日志里可区分 | PG 产物的 SKIP 文案 |
| 8 | report-only 要写明理由+误报率 | 不接 CI 必须解释 | `vacuity:audit` 100% 误报记录 |
| 9 | 不假装跑过 | 未验证要写"未验证 + 原因" | 容器/压测/CI 的标注 |

**这 9 条的共同点**：它们都不是"新功能"，而是**让"声称"与"事实"可区分**的机制。
对本仓这种"AI 驱动的交付底座"来说，这比任何单个门禁都重要。
